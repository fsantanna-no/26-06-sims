## How the vcs TCP model works (verified in source)

- `freechains --root=R daemon start --port=P --hub`
    - runs `git daemon --base-path=R/chains/ --export-all`
    - `--hub` adds `--enable=receive-pack` (accept pushes)
    - upload-pack stays on by default (accept fetches)
    - so one `--hub` daemon serves BOTH send and recv
    - src: `src/freechains.lua:215`
- `chain '#c' sync recv <url>`  = `git fetch` (pull)
    - src: `src/freechains/chain/sync.lua` (recv branch)
- `chain '#c' sync send <url>`  = `git push -o freechains=true`
    - remote `pre-receive` hook re-runs `sync recv` then rejects
      the push with "Freechains: OK" (expected)
    - hook auto-installed on `chains add` init+clone
      (`src/freechains/chains.lua:107,159`)
    - src: `src/freechains/hooks/pre-receive`
- URL builder turns `localhost:P` into `git://localhost:P/<alias>`
    - default PORT 8330; src: `src/freechains/common.lua:78` (URL)
- Identity = the SSH pubkey string (80 chars, `ssh-ed25519 <b64>`)
  extracted from the signed commit, NOT a file path.
    - so the same keyfile yields the same author across peers
    - src: `src/freechains/chain/ssh.lua` (M.pubkey / M.verify)
- Virtual time = `--now=<sec>` per command (`CMD.now`), which sets
  `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` and persists into `G.now`.
    - no daemon-held clock; monotonic time travels with commits
    - reps consolidation scans fire when `time > G.now`
    - src: `src/freechains.lua:205`, `chain/common.lua` (apply)

## Old CLI -> vcs CLI mapping (TCP)

| original (common.lua)              | vcs (TCP)                                              |
|------------------------------------|-------------------------------------------------------|
| `freechains-host --port=P start D` | `freechains --root=D daemon start --port=P --hub &`   |
| `freechains-host --port=P stop`    | `freechains --root=D daemon stop`                     |
| `now <ms>` (daemon clock)          | `--now=<sec>` on each post/like (no separate step)    |
| `keys pubpvt 'pass'`               | `ssh-keygen -t ed25519 -N '' -C '' -f /tmp/u/<user>`  |
| `chains join '$chat' SHA` pioneer  | `chains add '#chat' init --pioneer=<pioneerpub>`      |
| `chains join '$chat' SHA` others   | `chains add '#chat' clone localhost:PIO`              |
| `chain c post M P --sign=PVT`      | `--now=ts chain '#c' post inline P --sign=<keyfile>` (add `--beg` if 0-rep) |
| `chain c heads blocked`            | `chain '#c' list begs`                                |
| `chain c like HASH --sign=PVT`     | `--now=ts chain '#c' like <N> action HASH --sign=<keyfile>` |
| `chain c consensus`                | `chain '#c' list order`                               |
| `peer localhost:P send c` (push)   | `--root=SRC chain '#c' sync send localhost:P`         |
| `peer localhost:P recv c` (pull)   | `--root=SRC chain '#c' sync recv localhost:P`         |

Notes (doc-verified, cli.md v0.20):
- `like`/`dislike` args = `<n> (action <id> | author <pub>)`.
  Target keyword is **`action`** (not `post`). `<n>` = reps spent.
  So unblock a beg = `like <n> action <hash>`.
- `reps` args = `(actions|authors|revokes)` or
  `(action <id> | author <pub> | revoke <id>)`.
- Author `<pub>` may be passed as the `.pub` **file path**
  directly (e.g. `reps author /tmp/alice.pub`) or as the
  `ssh-ed25519 ...` string — no `cat`/`ssh-keygen -y` needed.
- `--pioneer=<pub>` at `init` sets the founder(s); accepts a
  key file path (private ok, reads `.pub`) or key string;
  repeat for multiple pioneers. No content is posted at init.
- Welcoming a beg: `list begs` -> parked hashes;
  `chain like <n> action <hash>` merges/unblocks it.
- `send` requires the remote daemon on `--hub`; `recv` (fetch)
  works against a plain daemon (guide.md Sync example).
- `list` modes = `order | dag | begs | revokes`.
    - `dag` exposes branch structure -> use to count forks
      for item (c) in `peers.sh` (not just `order`).
- `get (metadata | payload) <id>` reads a post's bytes ->
  true payload baseline for item (a).
- two welcome forms (guide + reps.md Rule 3.a):
    - `like <n> author <pub>` = WHOLE amount to onboard
    - `like <n> action <id>` = split half post/half author,
      and is the ONLY form that unblocks a beg
    - so an author-like does NOT merge a parked beg
- misc verbs: `chains dir` (list), `chains rem`,
  `abandon <id> [--keep]`, `sweep` (erase revoked payloads);
  vote takes `--why=<text>` / `--file=<path>`.

## Doc-verified facts (v0.20 docs, 2026-08)

Browsed `doc/{cli.md,guide.md,reps.md}` at
`github.com/Freechains/freechains.vcs@main`; binary = `v0.20.0`.

- Reps constants (reps.md; differ from paper):
    - bootstrap 50000 reps split among pioneers (Rule 1.a)
    - post reward 1000, only after 24h, at most 1/day/author (1.b)
    - post cost 500 temporary, refunds within <=12h as succeeding
      reputed activity acknowledges it (Rule 2)
    - every like/dislike transfer burns a 10% tax (Rule 3.a)
    - author cap 50000 reps (4.b); post size cap 128 KB (4.c)
- Like split: like on `action` -> half to post + half to author
  (after tax); like on `author` -> whole amount. Dislike drains.
- Action states (guide): begging / accepted / revoked.
    - paper "blocked" == begging (parked beg, needs a like)
    - content removal = `revoke`/`unrevoke` (distinct from dislike);
      revoked payload erased, metadata stays in DAG
- Hard fork (guide): a branch settles once it has >=100 actions OR
  spans >=7 days; a `sync` that would reorder settled/frozen posts
  is refused with `ERROR : chain sync : hard fork`.
    - recover: `abandon` local tip, `recv` settled branch, repost,
      `send` (repost is free — original never happened)
    - AFFECTS multi-host sim (item c): long partitions can hard-fork
      -> sync often enough, or expect/handle refusals
- sync `<remote>` URL forms: `host` | `host:port` | `path` |
  `scheme://...` (default port 8330). git:// underlies but the
  bare `localhost:P` form is what the CLI expects.

## Beg/unblock mechanism (verified in source)

Key shift from the old system: a 0-rep plain post no longer
auto-blocks — it **errors** ("insufficient reputation"). The poster
must opt in with `--beg`, so the harness decides up front.

| step    | old Kotlin        | vcs (Lua/Git)                              |
|---------|-------------------|--------------------------------------------|
| 0-rep   | `post` -> BLOCKED | `post --beg --sign` -> commit parked on     |
| post    |                   | `refs/begs/beg-<hash>`, main HEAD reset     |
|         |                   | (`post.lua` beg block, `reset --hard HEAD~2`) |
| detect  | `heads blocked`   | `git rev-parse refs/begs/beg-<hash>` /      |
|         |                   | `chain list begs`                           |
| unblock | pioneer `like`    | pioneer `like <n> action <hash>` -> `like.lua` |
|         | `<hash>`          | detects beg, merges branch into main,       |
|         |                   | transfers reps, deletes the ref             |

Harness decision logic (replaces old post + `heads blocked`):

```
reps = `chain '#c' reps author <PUB>`
if reps < 500:  post --beg --sign=key ; pioneer like <n> action <hash>
else:           post --sign=key
```

Raw units (2026-08): the gate is the post COST 500, not 0 — a
signed post needs `reps >= 500`, else `--beg`. (chat-02.lua
already does `reps < 500`.) The beg is unblocked only by
`like <n> action <hash>` (merges the branch); `like author`
would NOT merge it. Item (d) "extra likes" accounting stays
harness-side (as in old `common.lua`) — no CLI query needed.

H=$($FC --now=100 chain '#spike' post inline 'hi im new' --beg --sign=/tmp/new)

$FC chain '#spike' list begs | grep -q $H && echo blocked_ok    # parked beg
$FC chain '#spike' list order | grep -q $H && echo MAIN_BAD || echo not_in_order

$FC --now=200 chain '#spike' like 1000 action $H --sign=/tmp/pio  # welcome

$FC chain '#spike' list order | grep -q $H && echo unblocked_ok
$FC chain '#spike' list begs | grep -q $H && echo REF_LEAK || echo ref_clean

defaults to real time (~2026 >> 200), firing consolidation scans
(`time > G.now`) that inflate the newbie's reps. Direction holds
either way, but `--now` keeps the numbers clean.

## Multi-peer TCP gossip (chat-03 / use-03 shape)

- pioneer peer creates the chain; all other peers `clone` from it
- per message:
    1. map author -> a fixed peer port (sticky)
    2. post signed by that user with `--now=ts`
    3. random `NSYNCS` distinct peers: bidirectional `sync send`
    4. unblock begs (see divergence below)
- final convergence sweep: `send` up the port range then back down
- this reproduces forks/blocked metrics (paper items c, d)

Peer/sync counts come from the sources, NOT the paper text:

| driver     | NPEERS | NSYNCS | cap   |
|------------|--------|--------|-------|
| `chat-03`  | 5      | 3      | 10000 |
| `use-03`   | 12     | 4      | 10000 |

Two behavioral divergences to preserve (or deliberately unify):

- `chat-03` also unblocks on the REMOTE peer after each sync
  (`fc_blocked(p)` -> pioneer like); `use-03` does not.
  This shifts the blocked ratio (item d) between the two drivers,
  so they are not directly comparable unless made uniform.
- both broadcast `fc_now` to ALL peers before each post (old daemon
  held a global clock). In the vcs there is no daemon clock: `--now`
  is per-command, so this broadcast simply disappears from the port.

## Four evaluation items (paper targets)

| item | metric              | paper chat | paper news |
|------|---------------------|------------|------------|
| a    | metadata overhead   | 10x        | ~41%       |
| b    | consensus init/incr | 125s/50ms  | ~65s/70ms  |
| c    | fork ratio          | 18%        | 14%        |
| d    | blocked ratio       | 3.7%       | 3.5%       |

Paper (d) is ONE discounted ratio, not two percentages:

```
(d) = (nlikes - U) / (nmsgs - U)
```

Discount one initial message + one welcoming like per user, on
BOTH numerator and denominator (paper example: 10 users, 110
msgs, 20 likes -> (20-10)/(110-10) = 10%).
`U` = welcomed users (pioneer posts but never begs, so U = 78 not
79 for the chat-02 10k run).

WARNING: the code's `(c) new` / `(d) extra` lines are NOT the
paper's items. Both letters are reused for a split of welcome
likes (new-user vs re-beg), each divided by raw `ns` with no
discount. Neither printed line equals the paper ratio; compute
(d) from the formula above. The paper's real item (c) is the
FORK ratio (18% chat), a multi-host metric measured in step 7,
never in this single-host run.
